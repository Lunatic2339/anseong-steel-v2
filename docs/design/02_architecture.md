# 02 기술 구조

## 장비

| PC-A (호스트 · 왼쪽 조종사) | PC-B (클라이언트 · 오른쪽 조종사) |
|---|---|
| Quest 3 (Link 유선) | Quest 3 (Link 유선) |
| 왼팔 외골격 ESP32 (USB 시리얼) | 오른팔 외골격 ESP32 (USB 시리얼) |
| 관객용 모니터: 왼쪽 조종사 1인칭 | 관객용 모니터: 오른쪽 조종사 1인칭 |

두 PC는 유선 LAN(스위치 또는 직결)으로 연결한다. 학교 와이파이에 의존하지 않는다.

헤드셋 연결:
- **시연은 유선 Link가 기본.** USB-C 3.0 Link 케이블 약 5m × 2(+예비 1). 헤드셋 선과 외골격 USB 선을 묶어 한 줄로 PC까지.
- **Air Link는 예비.** 개발 중에는 써도 된다(게임 코드는 유선·무선 구분 없음). 시연 당일 케이블 고장 시 전환하며, 이를 위해 PC에 랜선으로 연결한 전용 공유기를 챙긴다.
- 무선을 기본으로 하지 않는 이유: 시연장 와이파이 혼잡(헤드셋 2대 동시), 외골격 USB 선 때문에 조종사가 어차피 PC에 연결됨, 하루 종일 시연 시 배터리, 추가 지연.
- M6 테스트 때 가능하면 시연 장소에서 Air Link도 한 번 돌려본다.

## 누가 무엇을 계산하나

| 계산 | 위치 | 전송 |
|---|---|---|
| 자기 조종사 입력·보정·팔 IK·주먹 포즈 | 각 PC 로컬 | 자기 팔은 네트워크를 거치지 않음 |
| 머리·양손 자세 | 각 PC가 소유 | 비신뢰(Unreliable) 60Hz → 상대 PC가 100ms 버퍼로 보간해 그림 |
| 펀치 궤적 분류 + 주먹 접촉 | 때린 쪽 PC | `HitReport(side, kind, quality, clientTime, strikeId)` 신뢰 RPC → 서버 |
| 가드 상태 | 각 PC가 자기 팔 | 매 틱 owner-write 값 |
| 연계·부스트·피해·HP·페이즈 | 서버(PC-A) | NetworkVariable + 서버 → 클라이언트 이벤트 RPC |
| 보스 AI·공격 판정 | 서버 | 상태(공격 종류 + 시작 서버 틱) 복제 → 클라이언트는 같은 시점부터 애니메이션 재생 |
| 외골격·컨트롤러 진동 | 각 PC가 자기 장치만 | 로컬 명중 + 서버 이벤트 |

NGO 설정: Unity Transport 직결(`SetConnectionData(ip, 7777, "0.0.0.0")`), 틱 60. 승인 콜백에서 3번째 접속 거절. 클라이언트는 피해·HP를 직접 쓰는 RPC를 갖지 않는다. 서버는 보낸 클라이언트가 그 팔(side)의 소유자인지 검사한다.

**1인 양팔 모드**: 같은 코드를 한 PC가 호스트로 실행하며 양쪽 조종사를 모두 로컬로 맡는다. 네트워크 경로와 판정 경로가 같아야 한다(별도 오프라인 전용 규칙 코드를 만들지 않는다).

## 시점과 스케일

- 월드는 실제 크기. v026 모델은 임포트 시 약 1m라서 약 65배(임포트 후 실측해 맞춤). 보스도 같은 크기.
- XR Origin은 **확대하지 않는다**. 조종사는 사람 크기 그대로 로봇 **머리(Head) 좌석**에 선다. 눈 약 57.5m(M0-04, 10/17 결정. 가슴 상단 좌석은 가드 주먹이 눈보다 약 3m 위라 보스를 가렸다). M1에서 팔 조작·보스 공격이 들어간 뒤 한 번 더 비교하고 조종석 아트 전에 확정한다.
- 자기 로봇 머리는 두 PC 모두 숨긴다(그림자만 남김). 그래서 A-02 병합 때 머리 부품은 `Robot_Head` 렌더러로 따로 남긴다.
- **조종석 위치는 로봇 루트 기준 고정 오프셋**으로 둔다. 애니메이션되는 머리 뼈를 따라가지 않는다. 로봇이 약 61배라 클립에서 머리가 1cm 움직이면 카메라가 약 60cm 움직여 멀미가 난다. 회전은 로봇 정면의 yaw만 따른다. 맞았을 때의 흔들림은 뼈에서 물려받지 않고 작게 따로 넣는다. (M0-04 샌드박스의 `CockpitSeat`는 애니메이터를 끈 상태라 머리 뼈를 따라갔다. M1에서 바꾼다.)
- 팔 매핑: `로봇 주먹 목표 = 로봇 어깨 + (손 − 보정한 사람 어깨) × (로봇 팔 길이 ÷ 개인 팔 길이)`. 배율 약 35~40배. Head 좌석에서는 눈이 로봇 어깨보다 약 5m 높다(사람은 약 0.25m). 가드 주먹이 눈 기준 약 30° 아래로 보이며(사람 약 23°), 어색하면 어깨 높이 보정값으로 맞춘다(M1에서 조절 항목으로 노출).
- 모델에는 Spine1·Spine2·Neck·Shoulder 뼈가 없다(Hips·Spine·Head만). 팔 IK는 쇄골 뼈 없이 상완부터 푼다. 뼈 이름은 바꾸지 않는다(Mixamo 클립 바인딩 유지).
- 조종석은 실제 형상(바닥, 콘솔, 창틀). 렌더텍스처 중계 화면을 쓰지 않는다. 두 좌석 간격 = 실제 바닥 테이프 간격.
- 조종사 카메라는 절대 지연시키지 않는다. 로봇의 묵직함은 팔 반응(가속·감속)으로 표현한다.
- 고개를 돌려도 팔의 정면 기준은 돌지 않는다(보정 시 저장한 몸 정면 기준).

## 플레이어 로봇 몸 (팔만 조종, 몸은 코드·클립)

조종사가 직접 움직이는 것은 **두 팔뿐**이다. 로봇 몸 전체는 화면에 있고, 나머지는 아래처럼 코드와 기존 클립으로 움직인다.

| 부위 | 움직이는 방법 |
|---|---|
| 두 팔(어깨·팔꿈치·손목) | 조종사 손 → IK. 왼팔 = PC-A 조종사, 오른팔 = PC-B 조종사(1인 모드는 한 사람이 둘 다) |
| 손가락 | 주먹 포즈 고정 |
| 몸통·다리 | 대기 클립을 계속 재생하고, 그 위에 팔 IK를 덮어쓴다(애니메이션 → LateUpdate에서 IK 순서) |
| 접근·후퇴·회피 | 로봇 전체를 코드로 짧게 이동(0.4초 안팎) + 걷기·옆걸음 클립을 다리에만 재생 |
| 몸 회전 | 보스가 정면 ±20° 밖이면 초당 30° 이하로 코드가 회전 |
| 맞았을 때 | 몸통이 조금 휘청하는 연출(클립을 몸통에만, 짧게). 조종사 카메라는 거의 흔들지 않는다(멀미) |
| 머리 | **로봇 머리를 숨긴다**. 두 조종사 모두 머리 안 조종석에 있으므로 어느 PC에서도 보이지 않는다 |

- 판단 근거: 조종석이 머리 높이라 조종사 눈에 보이는 건 주로 두 팔과 아래쪽 가슴·다리다. 다리가 대기 자세로 서 있어도 어색하지 않다. 기존 레포에서 같은 v026 모델로 팔 IK가 동작한 것을 확인했다(`backup/local-1015`의 Practice 솔버).
- 관객에게는 **조종사 1인칭 화면만** 보여준다(각 PC 모니터에 헤드셋 화면을 그대로 띄움, Unity Game 뷰·빌드의 기본 미러). 3인칭 관객 카메라는 만들지 않는다. 그래서 로봇 몸 전체가 보이는 화면이 없고, 몸통 보정 작업도 하지 않는다.
- 1인칭 미러는 조종사 고개 움직임이 그대로 보여 관객이 어지러울 수 있다. 문제가 되면 M5에서 모니터 화면만 부드럽게 따라가는 방식을 검토한다(추가 렌더 비용 확인 후).
- 필요한 클립은 보스와 같은 뼈라 Mixamo 클립을 같이 쓴다(`04_art_spec.md` 애니메이션 목록).

## 구조물 파괴 (M5, 여유되면)

- 방식: **미리 쪼갠 조각으로 바꿔치기**. 멀쩡한 구조물 → 맞으면 Blender Cell Fracture로 미리 만든 조각(20~40개)으로 교체 → 물리로 무너짐 + 먼지·소리 → 조각은 약 6초 뒤 사라짐. 실시간 쪼개기는 하지 않는다.
- 판정: 로봇 팔·몸, 밀려난 보스, 돌진하는 보스가 구조물에 일정 속도 이상으로 닿으면. 부서진 구조물은 다시 부서지지 않는다.
- 네트워크: 서버가 "구조물 N번 부서짐"만 신뢰 RPC로 알린다. 조각의 물리는 각 PC에서 따로 돌린다(모양이 조금 달라도 연출이라 괜찮음).
- 재시작하면 모두 원래대로. 동시에 무너지는 구조물은 최대 2개.

## 팔 IK 요구사항

- 해석적 2본 IK. 팔꿈치 swivel은 컨트롤러 회전에서 연속 각도로 고르고 범위 제한 + 히스테리시스.
- 손목은 전완에 고정(손목만 꺾이는 펀치 방지). 그립을 놓으면 제한된 손목 회전 허용.
- 매 프레임 바인드 포즈 기준으로 **절대 재구성**(누적 회전 금지 → roll 드리프트 방지).
- 손이 팔 길이 밖이면 지수형으로 부드럽게 한계에 수렴. 너무 가까우면 내부구 처리.
- 어깨·팔꿈치가 180도 돌아가는 현상이 없어야 한다.
- 손가락은 펀치 상태에서 주먹 고정.

## 외골격

- 조종사 한 명당 **담당 팔 하나**: 조종사 A = 왼팔, 조종사 B = 오른팔(왼팔 장치의 좌우 대칭). 담당 팔 손에 Quest 컨트롤러를 평소처럼 쥐고, 손목·손 주변 약 10cm는 프레임·끈이 지나가지 않는다(컨트롤러 추적).
- 힘 방향: **팔을 펼 때 막는다**(10/16 결정). 펀치는 펴는 동작이므로 명중감이 여기서 난다. 끈은 당기기만 하므로 펼 때 끈이 길어지는 경로로 둔다.
- 구동: 평소에는 끈을 느슨하게 두고(팔이 자유로움), 이벤트가 오면 빠르게 감아 짧게 버틴 뒤 다시 푼다. 감는 시간이 지연이 되므로 게임이 미리 아는 순간에는 준비 명령 `P`를 먼저 보낸다.
- 순서: 책상 위 시제품(팔꿈치 관절 하나)으로 방향·세기·지연·안전을 먼저 확인 → 착용형 한 팔(11/12) → 11/19에 시연 투입 결정. 안 되면 책상형은 부스 체험용, 게임은 컨트롤러 진동만.
- 안전 세 겹: ① 펌웨어 워치독·저항 최대 0.5초·세기 상한 상수·켜질 때 0 ② 비상 정지가 모터 전원을 직접 끊음 + 퓨즈 ③ 일정 장력에서 끊어지는 약한 고리 + 손으로 1초 안에 풀리는 착탈부. 비상 정지·약한 고리 시험(T6)을 통과하기 전에는 사람이 차지 않는다.
- 자세한 설계 근거: 총괄 채팅의 PDF「외골격 진행 평가와 설계 가이드」, 작업 순서는 `docs/tasks/H-01-exoskeleton-prototype.md`.

## 외골격 시리얼 프로토콜

115200bps, 한 줄 ASCII, 줄 끝 `\n`.

| PC → ESP32 | 뜻 | 게임에서 보내는 때 |
|---|---|---|
| `P,<ms>` | 준비: 느슨한 끈을 약하게 감아 둠. ms 안에 `R`이 안 오면 다시 풂 | 보스 공격 예고 시작(1.2~2.0초 전), 펀치 궤적이 인식된 순간(접촉 0.1~0.2초 전) |
| `R,<세기 0-255>,<지속ms>` | 저항. 펌웨어가 지속을 최대 500ms로 자름 | 명중(약 120ms), 가드 접촉(약 300ms) |
| `X` | 즉시 해제 | 부스트 점화, 일시정지·종료, 연결 끊김 |
| `H` | 살아 있음 신호 | 100ms마다 |

ESP32 → PC (10Hz, 기록용): `S,<상태>,<출력>,<오류코드>` 예: `S,RESIST,180,0`. 상태는 `IDLE`·`PRE`·`RESIST`·`RELEASE`·`SAFE`.

- 펌웨어: 200ms 동안 아무 명령도 없으면 `SAFE`(출력 0). `IDLE`에서 `R`이 바로 오면 `PRE`를 건너뛰고 감으면서 `RESIST`로 간다. 세기 상한·감는 방향은 펌웨어 맨 위 상수. 명령을 받으면 보드 LED를 켜서 지연 측정(240fps 촬영)에 쓴다.
- 세기 값과 실제 장력(kg)은 다르다. 책상 시제품의 세기표(`Hardware/Exo/`)를 보고 게임 쪽 세기를 맞춘다.
- Unity: 별도 스레드에서 포트 쓰기, 포트가 없거나 끊기면 조용히 비활성(게임 진행 영향 없음). Api Compatibility Level = .NET Framework.

## 성능 목표

- Link에서 90fps 유지(72fps 하한). GPU 여유를 위해 외부 카메라 추가 렌더 없음.
- v026 모델은 SkinnedMeshRenderer 291개·재질 124개 → 수십 개 이하로 병합, 텍스처 아틀라스.
